# Load Test Report — 2026-08-23

**Constrained-hardware capacity test: 1 CPU / 2GB RAM, k6 ramp 0 → 500 → 1000 VUs**

This is the real, executed run that `load-tests/README.md` (previous pass)
could not complete because k6 and a working Docker engine weren't available.
Both are available now. This report contains actual numbers from an actual
run — no informal Node-script stand-in, no untested script.

## Headline finding

**The app, capped at 1 CPU / 2GB RAM, cannot serve even light concurrency
acceptably, and falls over completely well below the 500-VU baseline the
test targeted.**

- At ~19 concurrent VUs (first ~10s of the ramp), median page-load latency
  was already **9.7 seconds** — 10x over the script's own `p(95)<1000ms`
  threshold, before the ramp had even reached the "warm-up" 200-VU stage.
- By ~120 VUs (~1 minute in), median latency was **16.2s**, p95 **43.2s**,
  with a 6% request-failure rate already showing up.
- By ~200-220 VUs (~2 minutes in, still short of the 500-VU baseline target),
  the app was **57% failed requests** and median latency hit k6's 60s HTTP
  timeout ceiling.
- From roughly the 3-minute mark onward — i.e., for the entire remainder of
  the 500-VU hold and the entire 1000-VU spike — **the app was saturated**:
  median (p50) latency pinned at k6's 60s request timeout, p95/p99 likewise
  at or past 60s, and 60-90%+ of requests failing (timeout or non-200).
- **Practical ceiling for acceptable UX (sub-2s p95) on this exact
  container: well under 20 concurrent users.** The container never
  recovered once concurrency climbed past roughly 100-150 VUs — it did not
  gracefully degrade, it collapsed into a persistent request backlog that
  never drained even as the ramp continued climbing.
- The bottleneck was unambiguously **CPU, not memory**. `docker stats`
  showed the single allotted CPU pinned at 95-115% (i.e., fully saturated)
  from about 2 minutes into the run onward, for the rest of the test, while
  memory usage peaked at only **~564-726 MiB of the 2GiB cap (≤36%)** — the
  container was never anywhere near an OOM condition. Under this cap, CPU
  runs out roughly an order of magnitude before memory would.
- The container did **not** crash or OOM-kill — it stayed technically "up"
  the whole time, just unable to drain its request queue. From an
  operator's perspective this would look identical to an outage: every
  request past the first ~100-150 concurrent users effectively times out.

This is a dramatically lower ceiling than the previous (unconstrained-laptop,
multi-core) ad hoc numbers in `README.md` suggested (which saw p95 ~2s at 50
concurrent, ~2.7s at 100). That's expected and is exactly the point of this
test: the previous numbers were produced on an 8-logical-core laptop running
`next start` with the full host's CPU behind it. Pinning the same build to a
single core reproduces what a small/entry-tier constrained VM (a common
budget cloud instance shape: "1 vCPU / 2GB") would actually deliver, and the
answer is: not much, for this SSR-heavy, auth-gated app.

Auth note: had to add `AUTH_TRUST_HOST=true` to the container's environment.
Without it, Auth.js v5 rejected every `/api/auth/*` call with an
`UntrustedHost` 500 (the container listens on :3000 internally but is
published externally as :3100, and Auth.js's host-inference doesn't trust
that mismatch by default). This is a load-testing-only workaround, not
something to carry into a real deployment without deliberately configuring
trusted hosts.

## Methodology

1. Built `load-tests/Dockerfile.loadtest` (new — this app has no other
   Dockerfile; the documented deployment path is pm2 + Nginx, unchanged) and
   `load-tests/docker-compose.loadtest.yml` (new), both purely for this test.
2. `docker compose -f load-tests/docker-compose.loadtest.yml up --build -d`
   — builds a real `next build` production bundle inside the image, starts
   it with `next start`, capped at 1 CPU / 2GB.
3. Verified `/login` and `/api/health` returned 200 from the containerized
   app before running any load.
4. Ran the existing, unmodified `load-tests/ramping-load.js` (0 → 200 → 500
   VUs, hold, spike to 1000, hold, ramp down — 15 minutes total, per the
   script's own `stages` — this already matches the "500 baseline / 1000
   peak" ask, so no script changes were needed) via:
   ```
   BASE_URL=http://localhost:3100 k6 run \
     --out json=load-tests/results/ramping-load-2026-08-23.json \
     load-tests/ramping-load.js
   ```
   Console output: `load-tests/results/ramping-load-console-2026-08-23.txt`.
   Raw NDJSON: `load-tests/results/ramping-load-2026-08-23.json` (~38MB,
   136k lines — every individual HTTP data point, not just the summary).
5. In parallel, sampled `docker stats --no-stream` on the app container
   every ~15s for the duration of the run:
   `load-tests/results/docker-stats-2026-08-23.tsv`.
6. Ran `write-path-concurrency.ts` (unmodified) **inside the same
   1-CPU/2GB-constrained container** via `docker exec`, at concurrency 50
   and 100, to isolate the raw database write path from the HTTP/SSR
   rendering path.
7. Tore down the containers/image afterward (see Cleanup).

### Overall run totals (k6's own summary)

- **10,739** total HTTP requests attempted, **10,098** completed with a
  duration recorded, **6,225 failed (58.0% error rate)** against the
  `http_req_failed` threshold of `rate<0.01` — failed by nearly 60x.
- `http_req_duration`: avg **41.75s**, p90 **60.0s**, p95 **60.0s** —
  threshold `p(95)<1000ms` failed catastrophically.
- **11,497** scripted checks ran; only 45.75% passed.
- Both configured thresholds (`http_req_duration`, `http_req_failed`) were
  reported as **crossed** by k6 at the end of the run — this was an honest
  failing run, not tuned to pass.

| `tasks_list` | 399 | 31.0s | 47.1s | 51.2s | 19.5% |
| `wedding_detail` | 374 | 32.8s | 49.6s | 60.0s | 9.1% |

The single worst offender by far is `/api/auth/csrf` — the very first call
every VU's iteration makes before it can even attempt to log in. With a
sleep-free login flow hit by hundreds of new VUs per ramp step, CSRF-token
fetches piled up behind the single CPU core faster than anything else,
which explains why login itself (`callback/credentials`) shows a
deceptively "better" 0% error rate: only the requests that survived the CSRF
bottleneck ever got that far, so that row is heavily survivorship-biased,
not evidence that login is fine under load.

### Container resource utilization (`docker stats`, sampled every ~15-30s)

| Time | CPU % (of 1 allotted core) | Memory | Memory % of 2GiB cap |
|---|---|---|---|
| Start (idle) | 0.02% | 118 MiB | 5.8% |
| ~70 VUs in | 97.7% | ~228 MiB | 11.1% |
| ~300 VUs in | 98.9-102.4% | ~330-350 MiB | 16-17% |
| 500-VU hold | 99.7-102.8% | 413-465 MiB | 20-23% |
| 1000-VU peak | 95-114% | 486-568 MiB | 24-28% |
| End of run (drain) | 98.9-101.9% | 548-726 MiB | 27-35% |

CPU is pinned at (or fractionally over, from scheduler burst accounting)
100% of the single allotted core continuously from roughly the 1-minute
mark of the run onward — i.e., for the entire remainder of the test. Memory
climbed slowly and linearly (consistent with accumulating queued
request/response buffers and Node's GC lag under CPU starvation) but never
exceeded ~36% of the 2GiB cap. **This container's ceiling is CPU, full
stop — the 2GB memory allowance was never remotely close to being the
limiting factor**, and doubling or quadrupling memory alone would not have
helped.

### Write-path (`write-path-concurrency.ts`) inside the same constrained container

Run via `docker exec` inside the 1-CPU/2GB container, hitting the real
Prisma write path directly against the same DB (bypassing HTTP/SSR — see
the script's own documented scope limitation in `README.md`):

| Concurrency | Total requests | Success | Failed | p50 | p95 | max | Wall time |
|---|---|---|---|---|---|---|---|
| 50 | 300 | 300/300 (100%) | 0 | 172.9ms | 2,177.8ms | 2,208.0ms | 3.2s |
| 100 | 500 | 500/500 (100%) | 0 | 244.2ms | 1,201.7ms | 1,292.0ms | 2.6s |

**Zero errors at either concurrency, even under the same 1-CPU cap that
broke the HTTP/read path.** This is a real and useful contrast: raw Prisma
writes queue politely behind the connection pool (`max: 10`) and the single
CPU core and simply take longer per call as concurrency rises — they don't
time out or throw. The thing that collapsed under load wasn't the database
or Prisma; it was the HTTP-request-handling / React SSR-rendering /
Auth.js layer sitting in front of it, which has to do meaningfully more
per-request CPU work (route matching, session decryption, server-component
rendering, CSRF token generation) than a bare `prisma.lead.create` call.

## The actual answer: how much load can this app handle on 1 CPU / 2GB?

**Far less than 500, and nowhere close to 1000.** Based on the per-minute
breakdown:

- **Acceptable (sub-2s p95, matching a reasonable internal-tool bar)**:
  did not hold at any point in this run, including the very first ~19-VU
  sample (already 9.7s median). A finer-grained ramp starting below 19 VUs
  would be needed to find the exact sub-20-VU ceiling, but this run
  establishes with confidence that it is **well under 20 concurrent users**.
- **Functionally broken (p50 pinned at the timeout ceiling, majority of
  requests failing)**: by roughly **200-250 concurrent VUs**, i.e. still
  inside the ramp toward the 500-VU baseline, well before the 500-VU hold
  or the 1000-VU spike were ever reached.
- The app **never recovered** once past that point — it stayed saturated
  through the entire 500-VU hold, the 1000-VU spike, and most of the
  ramp-down, meaning there is no higher "it actually copes at 500/1000"
  data point to report: the ceiling was crossed early and stayed crossed.

## Honest caveats

- **Postgres was not resource-constrained in this test.** It ran as the
  host's existing, already-running local instance, with the full host
  machine's 4 cores / 16GB behind it. This means the numbers above measure
  the app container's ceiling in isolation, assuming an effectively
  infinite-capacity database next to it — a real single-VM deployment where
  Postgres shares the same 1 CPU / 2GB would hit its ceiling **even earlier**
  than what's reported here, not later. This report is a best case for the
  app-tier-only bottleneck, not a full realistic single-box production
  topology.
- k6's default HTTP request timeout (60s) means every number above labeled
  "60.0s" is really "no response before k6 gave up" rather than a true
  measured server response time — the real tail latency under saturation
  could be even higher (or the request might genuinely have hung
  indefinitely server-side); this run cannot distinguish those cases.
- The read-path numbers are dominated by `/api/auth/csrf` congestion at the
  very front of every iteration's login flow. This is somewhat particular
  to this script's structure (every VU re-logs-in every iteration rather
  than reusing a session for multiple page views), which is more login-churn
  than a realistic staff workflow — but it's also not an unreasonable stress
  pattern, and the underlying finding (single CPU core saturates fast under
  concurrent Node.js/Next.js SSR + Auth.js work) would still show up, just
  perhaps a little later, with a lower-login-churn workload.
- The write-path numbers, while genuinely zero-error, only exercise the
  Prisma/Postgres layer directly and skip HTTP/auth/RSC entirely (documented
  limitation carried over from the original script/README) — they are not
  evidence that the full write path (a real `createLeadAction` Server
  Action call over HTTP) would hold up as well; given the read path's
  results, it almost certainly would not, once concurrent HTTP-layer CPU
  contention is added back in.
- This deployment's realistic expected concurrency (see
  `load-tests/README.md`'s existing analysis) is more like 20-50 staff
  sessions, not 500-1000 — so while the headline number here sounds alarming
  ("collapses under 200 users on 1 CPU"), the more directly relevant
  takeaway for this specific deployment is: do not run this app on a
  1 vCPU / 2GB box even for realistic (20-50 user) staff concurrency
  without further profiling — this test didn't get fine-grained enough at
  the low end (below ~20 VUs) to say for certain whether 20-50 concurrent
  users would be fine or already degraded on 1 CPU, only that 100+ clearly
  is not.

## Reproducing this test

```
# From app/:
docker compose -f load-tests/docker-compose.loadtest.yml up --build -d
curl http://localhost:3100/login   # confirm 200 before proceeding

BASE_URL=http://localhost:3100 k6 run \
  --out json=load-tests/results/ramping-load-<date>.json \
  load-tests/ramping-load.js

# In a separate terminal, while the above runs:
while true; do docker stats --no-stream load-tests-app-1; sleep 15; done

# Write-path, inside the same constrained container:
docker exec -e DATABASE_URL="postgres://postgres@host.docker.internal:5433/weddingos?sslmode=disable" \
  load-tests-app-1 npx tsx load-tests/write-path-concurrency.ts 50 300

# Cleanup:
docker compose -f load-tests/docker-compose.loadtest.yml down
```
